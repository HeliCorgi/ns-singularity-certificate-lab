# Verified Results Registry

**Audience.**  A third party who wants to know exactly what this repository
proves, on what trust basis, and how to reproduce each item.  This document is
an index with stable IDs; the sources of truth are the Lean library
(`formal/`), the Python certificate modules (`src/ns_certificate_lab/`), the
emitted payloads (`outputs/`), and the research notes
(`docs/research_notes/`).

**This file is the complete list.**  The README carries only a few
representative examples; every registered result lives here.

**This repository does not solve, and does not claim to advance, the Clay
Millennium Problem.**  No entry below is a singularity statement.  A
certificate-chain stop time is a limitation of the method, never a property of
any solution.  See the scope table at the end.

**Read this before trusting any entry:**

* **The standard-axiom report is not an "axiom-free" claim.**  Every
  Lean-verified entry is kernel-checked and reports at most
  `[propext, Classical.choice, Quot.sound]` under `#print axioms` — the three
  standard classical axioms of Lean/mathlib, i.e. the ordinary foundation on
  which all of mathlib sits.  "No project axioms" means exactly that: no
  `axiom` declaration, no `sorry`, no `admit` anywhere in `formal/`.  The one
  theorem that is literally axiom-free (pure propositional logic) is
  `NSSingularity.cond_to_uncond` (VR-L-007).
* **The status vocabulary is exactly five values, and they are never blurred.**
  * **Lean-verified** — a kernel-checked theorem with no project axioms.  The
    VR-L family, and nothing else.  A Python-checker result is **never** called
    Lean-verified.
  * **certificate-verified** — an independent full-recomputation Python checker
    re-derives every recorded relation from the payload's own stored numbers in
    exact rational (or exact rational interval) arithmetic.  The label covers
    the entry's **finite** content only.  The VR-C family.
  * **hybrid** — the result combines Lean-verified finite logic,
    certificate-verified rational computation, **and** classical analysis that
    is audited but **not** Lean-formalised.  The reissued Track-P chain PDE
    conclusions (`outputs/track_p_chain_reissued_v2/`) are the archetype: they
    are not *conditional*, because the EXT statements are closed by audited
    paper proofs; and they are not *Lean-verified*, because that analysis is not
    formalised and never will be axiomatised here.  VR-COND-004, VR-COND-005.
  * **conditional** — a named unproved external assumption is still in the
    trust chain.  The v1 payloads keep the pre-audit wording and record
    EXT-P1/P2/P3 with `proved: false`: `outputs/track_p_slab_v1/`,
    `outputs/track_p_chain_v1/`, and the v1-worded `outputs/track_p_chain_h3_v1/`.
    VR-COND-001/002/003.
  * **numerically observed** — binary64 only: no interval enclosure, no checker,
    no theorem.  The VR-N family.
  * Where an entry genuinely spans two of these (VR-N-004), the status names
    which part is which instead of averaging them.  `VR-COND-006` is a register
    of open named gaps, not a result, so it carries none of the five.
  * "Candidate" is **not** a status.  The word appears in prose only for a
    would-be bridge to a Clay statement, and no entry in this registry is one:
    every such bridge is open and recorded as open.
* **`proved: true` on an external-theorem record means "audited paper
  proof".**  In `EXTERNAL_THEOREMS_AUDITED`
  (`src/ns_certificate_lab/torus_aposteriori.py`) and in every reissued chain
  payload, `proved: true` means: a complete classical-analysis proof written
  in this repository that survived a two-stage adversarial audit
  (`docs/research_notes/ext_p1_p2_p3_audit.md`).  It never means
  Lean-formalised; every such record carries a `closure` block with
  `method: "audited_paper_proof"`, `lean_formalised: false` and
  `axiomatised_in_lean: false`, and the checker rejects any payload claiming
  otherwise.  Lean axiomatisation of external analysis is forbidden in this
  repository.
* **Counts drift.**  Lean compilation-job counts (the `8659 jobs` note in
  `formal/AxiomAudit.lean` — `lake build` at HEAD reports `8672 jobs`, which is
  exactly the drift that note warns about, and jobs are not theorems), pytest
  test counts, and payload byte sizes drift
  as the tree evolves.  The Python side is re-verified by CI on every push
  (`.github/workflows/tests.yml`).  **The Lean gate is not in CI**: it is the
  manual command block below (`lake build` plus
  `lake env lean AxiomAudit.lean` under the toolchain pinned in
  `formal/lean-toolchain`, currently `leanprover/lean4:v4.32.1`), and it must be
  run by hand before trusting a VR-L row after a `formal/` change.
* **Reproduction commands** are given relative to the repository root and
  assume the project virtual environment is active (README, section
  §Reproduce / 再現手順 → Quick verification、および docs/reproducibility.md §1).  On this machine `./.venv/Scripts/python.exe` can be
  substituted for `python`.
* **The two commit columns.**  "first commit" is the commit that introduced the
  entry.  "latest verified commit" is the last commit that touched the entry's
  source file, read off with `git log -1 --format=%h -- <path>`; where an entry
  spans many files that move independently it reads
  `HEAD (CI re-verifies every push)` instead, and that phrasing is used only
  where CI actually covers the entry.  HEAD at the time of this revision is
  `fd1e1c5`; every hash below was checked with `git log -1`.  Turn labels used
  by earlier revisions resolve as: turn 9 = `d07a4f3`, turn 10 = `f369745`,
  turn 11 = `17d41df`.  All eighteen `formal/**.lean` files report `fd92cfe`
  because that commit added the Apache licence header to each of them; no
  mathematical content changed there, and the axiom gate was re-run on the
  present tree (see the VR-L preamble).
